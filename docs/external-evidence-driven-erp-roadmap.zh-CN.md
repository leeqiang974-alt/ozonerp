# Ozon ERP 外部证据驱动路线图

更新日期：2026-07-12

## 1. 纠偏目标

项目不再依据现有页面、内部设想或 AI 推测继续扩张。后续功能必须由三类证据共同驱动：

1. Ozon 官方 Seller API、Seller Edu 或真实店铺响应，定义平台事实。
2. 可运行的 GitHub 项目或成熟电商系统，提供工程实现和交互参考。
3. 本项目可回放 fixture 与受控真实 SKU，证明能力在当前环境有效。

任何能力都必须标记验证级别：`documented`、`mocked`、`locally_tested`、`real_read_verified`、`real_write_verified`。只有完成受控真实写入及结果回读，才能称为业务闭环。

## 2. GitHub 调研结论

### 值得借鉴

| 项目 | 可借鉴内容 | 不直接照搬 |
|---|---|---|
| `Shawn220528/ozon-erp` | NestJS + PostgreSQL + Redis/BullMQ、多店铺隔离、JWT、密钥加密、商品/订单/财务/退货/评分模块划分 | README 声明不等于全部能力已在真实账号验证；需逐模块读代码和测试 |
| `a-ulianov/OzonAPI` | 异步请求、多账户、限流、自动重试、Pydantic 数据模型、测试与覆盖率 | Python SDK 架构不直接替换当前 Node 服务 |
| `salacoste/ozon-daytona-seller-api` | TypeScript SDK 的 API 分类、类型模型、CI、覆盖率、兼容层 | 方法数量不能代替真实流程设计；先核实端点版本和生成代码质量 |
| `irenicaa/ozon-seller` | 分页迭代器、结构化请求/响应、HTTP 状态与 Ozon 错误码保留 | 接口覆盖有限，作为客户端设计样本而非完整 ERP |
| `pavelhalanin/ozon-seller-database` | 将商品、价格、库存、订单定期同步并规范化到 SQLite，形成店铺本地镜像 | 文件下载脚本和旧端点不能作为当前生产方案 |
| `ilyautov/marketplaces-mcp-ru` | AI 读取真实数据、结果带来源、写价格/库存前确认、schema-driven API 覆盖 | AI/MCP 不能绕过本项目预检、权限与审计 |
| `Oxonomy/ozon-seller-mcp` | 商品、库存、FBS/FBO、财务、评价、活动等运营动作地图 | 仓库体量小、测试与安全性不足，主要用作缺口索引 |
| Vendure | 目录、订单、库存、促销、队列、插件和后台管理的成熟领域边界 | 它不是 Ozon 专属 ERP，不能替代 Ozon 类目、审核和 Seller API 规则 |

### 不应作为基线

- 只有 Next.js/Create App 模板、静态页面或 README 宣称“全链路”的新仓库。
- 没有真实 API client、数据库迁移、任务队列、测试或错误回读的展示项目。
- 直接采集竞品并无确认发布、绕过验证码、硬编码远程后端或密钥的项目。
- 非官方但以“Ozon 官方 SDK”口吻进行营销、无法验证维护者和实现的仓库。

## 3. 真实卖家产品模型

ERP 首页不按技术模块展示，而按卖家每天的四类任务组织：

1. 今日待处理：审核失败、缺库存、待发货、价格风险、活动异常。
2. 商品上新：货源候选、草稿完整度、待确认字段、待提交、审核结果。
3. 店铺运营：在线商品、价格库存、订单履约、活动、退货和评分。
4. 风险与结果：哪个对象失败、业务原因、推荐动作、点击副作用、处理结果。

普通用户默认不接触 workflow node、payload JSON、reasonCode、prompt、API 原始响应和规则发布审计；这些内容进入二级诊断抽屉。

## 4. 1688 到 Ozon 的完整证据链

| 阶段 | 用户看到 | 系统必须证明 | 验收证据 |
|---|---|---|---|
| 货源采集 | 商品、供应商、价格区间、SKU、图片、尺重、采购风险 | 页面来源、采集时间、原始字段、解析问题 | 原始快照 + 标准化 fixture |
| 候选筛选 | 是否值得上、淘汰原因、预计成本 | 同品关系、采购价、起订量、供应稳定性 | 人工确认结果和原因 |
| SKU 规范化 | 颜色/尺寸/套装等可售变体 | 每个 SKU 的规格、采购价、图片、库存/起订信息 | 变体矩阵回放测试 |
| Ozon 类目/type | 推荐类目、备选及差异 | 当前官方类目树、type、必填属性、合法字典值 | 缓存版本、查询响应、人工选择 |
| 内容本地化 | 俄文标题、描述、属性解释 | 来源字段、翻译/AI 模型、禁止臆造的事实 | 中俄对照和人工确认 |
| 媒体处理 | 主图、SKU 图、详情图、风险图 | 原图来源、OCR、清理/翻译、OSS 映射、像素与内容质量 | 图片处理清单和预览确认 |
| 包装与合规 | 重量尺寸、原产国、敏感属性 | 尺重证据与单位转换，不能用 PDD/AI 猜可信尺重 | 来源可信度和人工补录 |
| 定价 | 成本、物流、佣金、汇率、利润、最低价 | 每个参数的来源、版本、生效时间和计算过程 | 可复算价格快照 |
| Preflight | 能否提交、最少修复项 | Ozon payload、本地质量闸、变体唯一性、价格风险 | 预检报告 |
| 人工提交 | 将写入什么、费用和影响 | 当前草稿哈希、店铺、SKU 数量、显式确认 | 提交审计事件 |
| 审核回读 | 成功/失败、具体 SKU/字段 | task_id、product_id、错误和警告标准化 | Ozon 回执快照 |
| 库存就绪 | 是否可售、哪个仓库、库存结果 | 商品状态、仓库状态、写前写后回查 | 库存对账记录 |

## 5. 前端重构原则

每个业务页面必须通过真实任务验证，而不是只做视觉稿：

- 页面首屏只保留当前对象、状态、阻塞原因和 1 个主要动作。
- 写操作按钮显示影响范围，并在确认后展示结果与可恢复路径。
- 空状态必须告诉用户如何获得真实数据，不能用虚构 KPI 填充。
- 列表、筛选、分页、加载、失败、部分成功、重复点击和恢复都要设计并测试。
- 业务语言优先，例如“缺少包装重量，无法计算物流成本”，而不是只显示 `PRICING_PACKAGE_MISSING`。
- 前端验收至少包含桌面端真实数据烟测、慢响应、接口失败、空数据和权限不足五种状态。

## 6. Claude 与 NVIDIA 的分工

### Codex

- 读取仓库、官方资料和真实响应，维护证据矩阵。
- 实现代码、测试、运行验证和项目文档。
- 对最终安全性与完成状态负责。

### 官方 Claude Code

- 在能够读取仓库时生成产品/架构 brief。
- 审查模块边界、用户任务、代码变更和回归风险。
- 输出只能作为评审意见，不能替代测试和真实平台证据。

### Claude NVIDIA

- 作为无工具、有限上下文的第二评审者。
- 适合：把技术状态翻译成卖家语言、比较两套方案、生成边界测试、审查已提供的 diff/证据摘要。
- 不适合：自主判断最新 Ozon API、猜测仓库文件、直接设计生产 payload、批准价格/库存/提交写操作。
- 输入必须包含明确的官方事实、GitHub 代码证据、当前 diff 和验收标准；输出必须带“不确定项”和“需验证项”。

建议评审顺序：`外部证据收集 → Codex 形成方案 → 官方 Claude 仓库评审 → Claude NVIDIA 独立反方评审 → Codex 按测试和真实回放裁决`。

## 7. 下一阶段执行顺序

### Phase A：证据与基线

1. 建立 Seller API 端点清单，记录当前版本、请求/响应 fixture、读写风险和本项目实现位置。
2. 建立 1688 真实商品 fixture 库，至少覆盖单 SKU、多颜色、多尺寸、套装、缺尺重和人机验证。
3. 给现有模块补验证级别，不再笼统标记“已完成”。
4. 整理未提交工作区，修复重复路由和测试数据污染。

### Phase B：单商品黄金路径

1. 只保留一个“上架商品”任务界面。
2. 用受控商品跑通采集、草稿、人工修复、提交、审核回读和库存就绪。
3. 每个失败都能回到具体业务对象和字段。
4. 连续完成至少 10 次真实回放后再扩批量能力。

### Phase C：店铺运营闭环

1. 商品状态与异常修复。
2. 库存写前写后对账。
3. FBS 打包、发运、取消和标签。
4. 活动加入、活动价校验、移出和回查。
5. 财务、退货和评分只在 API/真实数据打通后进入一级导航。

## 8. 完成定义

一个模块只有同时满足以下条件才可称为可用：

- 有官方或真实响应定义业务事实。
- 有数据库状态和幂等/重试策略。
- 有用户任务、空态、失败态和写操作确认。
- 有单元、契约和界面测试。
- 有受控真实账号回放记录。
- 有监控、审计和恢复方法。
- 文档标明验证级别、日期和仍存在的限制。
