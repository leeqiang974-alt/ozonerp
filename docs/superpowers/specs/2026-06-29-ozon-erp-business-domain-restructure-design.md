# Ozon ERP 业务域重构设计

更新时间：2026-06-29

## 背景

当前 Ozon ERP 前端已经沉淀了很多能力：1688 采集、Ozon 参照、上架草稿、工作流控制台、定价诊断、库存、订单、营销活动和系统配置。但这些能力在界面上仍然以技术流程、节点诊断和历史状态为中心，导致普通卖家进入系统后难以判断：

- 店铺现在经营得怎么样。
- 商品、订单、库存、活动和利润分别在哪里看。
- 当前风险属于哪个业务域。
- 上架流水线和工作流诊断应该从哪里进入。

本次重构目标不是新增一个待办页，也不是继续修单个 tab，而是把 ERP 信息架构从“开发者流程工具”调整为“电商卖家经营系统”。

## 目标

1. 首页成为店铺经营总览，而不是今日待办或工作流诊断墙。
2. 一级导航按完整电商 ERP 业务域组织，不能只覆盖用户举例说出的几个模块。
3. 上架流水线归入“上架中心”，作为二级 tab，不再支配整个 ERP 首页。
4. 工作流诊断定位为排障工具，只在上架中心或系统高级诊断中出现。
5. 每个模块都有明确边界，出现跨模块字段时按“模块串区 bug”处理。
6. 技术状态必须翻译为业务语言，让卖家知道问题、原因、下一步动作和点击后果。

## 非目标

- 不在本阶段调用 Ozon Seller API 提交商品。
- 不改真实库存写入、订单处理或活动操作的后端副作用。
- 不删除现有能力，只重新归位和收敛首屏表达。
- 不把 Dashboard 继续做成“今天待办中心”或“上架流水线首页”。

## 一级导航

一级导航表示业务域或经营职能，不表示技术流程节点。

1. 店铺总览
2. 商品管理
3. 选品采购
4. 上架中心
5. 订单履约
6. 库存仓库
7. 营销活动
8. 财务利润
9. 客户售后
10. 数据报表
11. 系统配置

这些模块是完整 ERP 结构的基线。用户提到“商品、选品、店铺管理……”时，省略号表示还应包含订单、库存、营销、财务、客户售后、报表和系统配置等业务域，不能只实现被点名的几个。

## 店铺总览

店铺总览是 ERP 首页。它回答“店铺现在怎么样”，而不是“今天让我先点哪个按钮”。

主内容区包含：

- 销售概况：今日、近 7 日、近 30 日销售额、订单数、退款/取消。
- 利润概况：销售额、采购成本、物流费、佣金、毛利估算、利润风险。
- 商品状态：在售、审核中、审核失败、缺库存、缺价、异常商品。
- 订单履约：待备货、待发运、运输中、取消、争议。
- 库存仓库：低库存、库存写入失败、仓库同步异常。
- 营销活动：进行中活动、可加入商品、活动价格风险。

今日待办只作为右侧窄栏或顶部提醒存在，例如：

- 今日需处理 5 件。
- 最高风险：审核失败 1 件。
- 库存写入失败 2 件。

提醒卡可以跳转到对应模块，但不能抢占首页主叙事。

## 模块边界

### 商品管理

管理 Ozon 商品卡及状态：

- 商品列表。
- 在售、审核中、失败、归档、缺价、缺库存。
- 商品卡异常和状态同步。
- 商品级价格、库存、活动参与状态的摘要。

不处理：选品采集、上架草稿编辑、订单发货、活动配置。

### 选品采购

管理货源与选品：

- Ozon 竞品/参考商品。
- 1688 货源、候选池、供应商。
- 采购价、SKU、尺重、图片素材。
- 选品风险和货源替换建议。

不处理：Ozon 提交、库存写入、订单履约、活动操作。

### 上架中心

管理商品从草稿到 Ozon 审核的流程。二级 tab 包含：

- 上架草稿。
- 类目属性。
- 文案图片。
- 定价预检。
- 提交审核。
- 审核回馈。
- 工作流诊断。

上架中心可以展示流程，但必须以业务动作组织：缺什么、为什么缺、改哪里、下一步是否安全。

### 订单履约

管理 FBS 订单：

- 待备货。
- 待发运。
- 运输中。
- 取消。
- 争议。
- 异常订单。

不处理：商品上架字段、选品和库存配置。

### 库存仓库

管理仓库和库存：

- 仓库列表。
- 库存读取。
- 库存写入。
- 库存失败队列。
- 低库存提醒和补库存建议。

不处理：订单详情、上架属性、营销活动。

### 营销活动

管理 Ozon 活动：

- 活动列表。
- 活动商品。
- 可加入商品。
- 移出活动。
- 活动价格策略和活动风险。

如果营销活动页出现平台分类、无忧易售信息、描述、产品采集图、标题、类目属性或上架表单字段，必须按模块串区 bug 修复。

### 财务利润

管理经营财务视角：

- 销售额。
- 采购成本。
- 物流费用。
- Ozon 佣金。
- 毛利和利润率。
- 原价、最低价和价格风险。
- 后续可扩展结算、广告费和活动折扣。

### 客户售后

第一阶段可占位，但必须保留业务域：

- 评价。
- 退货。
- 纠纷。
- 客服问题。
- 差评风险。

### 数据报表

管理跨模块分析：

- 销售趋势。
- 商品表现。
- 库存周转。
- 选品效果。
- 上架成功率。
- 异常趋势。

### 系统配置

管理系统能力和高级诊断：

- 店铺 API。
- Ozon 类目和属性字典。
- 1688 插件和 Ozon 插件状态。
- 自动化规则。
- 运行日志。
- 开发缺口和高级诊断。

普通业务操作不得被塞进系统配置；系统配置也不能成为日常经营入口。

## 工作流诊断定位

工作流诊断不是 ERP 首页，不是日常经营总览。它是上架中心里的排障工具。

工作流诊断必须回答：

- 哪个商品卡住。
- 卡在哪个业务步骤。
- 为什么卡住。
- 需要改哪个字段或切换哪个策略。
- 下一步按钮是否会产生外部副作用。

它可以保留节点、输入输出、payload、事件日志，但默认折叠高级内容。首屏必须是业务诊断，而不是 JSON、节点日志或技术状态。

## 状态语言映射

以下技术状态不能直接作为核心文案出现：

- `waiting_human`
- `node_failed`
- `blocked`
- `manual_intervention`
- `workflow_run`
- `preflight_blocked`

必须翻译为业务语言，例如：

- 缺少必填属性，需要补类目字段。
- 定价风险，当前利润过低。
- Ozon 审核失败，需要修复商品卡字段。
- 货源尺重缺失，无法计算物流费。
- 浏览器遇到人机验证，需要人工通过后继续。
- 库存写入失败，需要检查仓库或商品状态。

## 迁移规则

现有能力按以下方式迁移：

- Dashboard 的大段上架流程卡迁到上架中心。
- Dashboard 的工作流焦点缩成右侧风险提醒和跳转入口。
- 工作流控制台从主叙事降级为上架中心二级 tab 或系统配置高级诊断。
- Ozon 学习、图片风格、GPT 单品指导归入选品采购或上架中心的素材辅助区。
- API 对齐、插件状态、字典刷新、开发缺口归入系统配置。
- 商品状态、订单、库存、营销活动必须成为独立业务域，而不是折叠在驾驶舱内的附属卡片。

## 首屏验收标准

打开 ERP 首页后，首屏必须能回答：

1. 店铺今天/近 7 日销售和订单情况如何。
2. 商品总体状态是否健康。
3. 库存和订单是否有风险。
4. 利润或价格是否有异常。
5. 今日提醒有哪些，但提醒不能压过经营总览。

首屏不得以工作流节点、技术日志、JSON、开发缺口或上架表单为主。

## 测试策略

前端静态测试需要新增或调整：

- 一级导航包含完整 ERP 业务域。
- Dashboard 暴露店铺销售、商品、订单、库存、利润和活动摘要。
- Dashboard 的今日待办只作为提醒区，不是主区域。
- 上架流水线只出现在上架中心。
- 工作流诊断不作为首页主模块。
- 营销活动、订单、库存、商品、上架中心各自不出现跨模块字段。
- 技术状态文案不能直接出现在首屏核心卡片。

回归验证：

- `node --test test/frontend-static.test.js`
- `npm test`
- `npm run lint`

## 分阶段实施建议

### 阶段 1：信息架构骨架

重建一级导航和二级 tab 结构，保留现有页面 ID 或建立兼容映射，避免一次性破坏事件绑定。

### 阶段 2：Dashboard 经营总览

把首页改为店铺经营总览，今日提醒降级为侧边栏。先用现有 API 和本地状态汇总，不引入新外部副作用。

### 阶段 3：上架中心归位

把上架流程、工作流诊断、预检、提交、审核回馈重新组织为上架中心二级 tab。

### 阶段 4：模块串区治理

为每个模块加静态边界测试，防止商品、选品、营销、订单、库存、财务、系统配置互相混入字段。

### 阶段 5：业务语言翻译层

建立状态到业务原因、推荐动作和后果说明的映射层，用于 Dashboard、工作流诊断和提醒卡。

## 风险

- 现有 `public/app.js` 很大，直接大改容易引入回归，应分阶段做静态测试保护。
- 旧页面 ID 和事件绑定较多，迁移时要保留兼容层或逐步重命名。
- 真实 Ozon 提交、库存写入和 GPT/Image 成本动作必须继续保留人工确认和安全闸。
- 如果只改导航不改首屏叙事，用户仍会觉得系统像技术工具；因此 Dashboard 阶段必须优先落地。
