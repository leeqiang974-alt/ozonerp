# Ozon ERP 自动增量校正与后台数据库设计

## 目标

ERP 页面始终优先读取后台数据库。运营人员选择店铺或进入左侧功能页后，系统按照资源的缓存策略自动判断是否需要访问 Ozon；同一店铺、同一资源在最近一次成功同步后的 5 分钟内不重复请求。同步在页面数据展示之后触发，不阻塞本地数据浏览。

正式环境使用 PostgreSQL，SQLite 仅用于本地单机开发和自动化测试。所有金额继续固定为 CNY，所有 Ozon 调用在本阶段保持只读。

## 方案选择

采用“数据库同步状态 + 页面按资源触发 + 后台增量任务”的方案，而不是浏览器保存时间戳或每次进入页面全量同步。

- 浏览器时间戳不能协调多用户、多标签页和多个 ERP 实例，因此不作为新鲜度依据。
- 仅靠 `sync_runs` 历史记录可查询最后成功时间，但不适合原子加锁和保存长期资源游标，因此新增独立同步状态表。
- PostgreSQL 提供正式环境所需的并发、事务、索引、备份和行级锁；测试继续使用 SQLite，保证测试快速且独立。

## 数据模型

新增 `sync_states` 表，每个店铺、每种资源唯一一行：

| 字段 | 含义 |
|---|---|
| `shop_id`、`resource` | 唯一资源键，保证店铺隔离 |
| `last_success_at` | 最近成功完成时间，是 5 分钟新鲜度判断的唯一依据 |
| `cursor` | 商品滚动分页游标或其他资源游标 |
| `window_end_at` | 订单最近成功同步窗口的结束时间 |
| `lease_owner`、`lease_expires_at` | 短租约锁，防止多页面或多实例重复同步 |
| `last_error` | 可读、脱敏的最近错误摘要 |
| `updated_at` | 状态更新时间 |

`sync_runs` 继续保存每次运行的审计历史，不承担资源当前状态。业务页面继续读取 `products`、`fbs_postings`、`listing_drafts`、`ozon_category_cache` 等本地表。

数据库配置规则：

- 正式环境的 `DATABASE_URL` 必须是 PostgreSQL URL，并使用连接健康检查和连接池。
- SQLite URL 只允许出现在开发或测试环境。
- 引入 Alembic 管理正式数据库迁移；现有 SQLite 小型增量迁移在测试过渡期保留，后续统一收敛。
- API Key 仍只保存加密密文，迁移和日志均不得包含明文凭据。

## 页面与资源映射

选择店铺后，当前左侧页面立即从本地 API 加载数据，然后向后台提交一次轻量校正请求：

| 左侧页面 | 自动校正资源 | 缓存有效期 |
|---|---|---|
| 经营概览 | 商品、FBS 订单 | 5 分钟 |
| FBS 订单 | FBS 订单、缺失的订单商品图片 | 5 分钟；已有图片不重复获取 |
| 商品与库存 | 商品 | 5 分钟 |
| 商品上架 | 本地草稿；类目按需校正 | 草稿不访问 Ozon；类目 24 小时 |
| 同步中心 | 只读同步记录 | 不自动触发业务同步 |
| 店铺管理、定价与营销 | 当前本地数据 | 本阶段不额外调用 Ozon |

切换店铺和切换左侧页面使用同一触发函数。前端对同一个正在进行的请求去重，但是否真正同步必须由后端 `sync_states` 决定，不能信任浏览器状态。

## 增量校正规则

### FBS 订单

首次同步读取最近 7 天。后续以 `window_end_at - 10 分钟` 为开始时间，以当前时间为结束时间，形成重叠窗口；幂等 upsert 用 `shop_id + posting_number` 去重。重叠窗口用于捕获订单状态变化和短暂延迟。分页必须持续到当前窗口结束，成功处理全部页后才更新 `last_success_at` 和 `window_end_at`。

### 商品

Ozon 商品列表的 `last_id` 是分页游标，不视为可靠的“变更时间游标”。因此采用滚动分页校正：每次自动校正从 `sync_states.cursor` 继续读取有限页数并幂等 upsert；到达末页后清空游标，下个周期重新从第一页开始。每天至少完成一次完整滚动周期。人工“强制完整校正”可以重置游标并跑完整周期，但默认页面进入不会全量读取。

### 图片

只查询图片为空或图片校正时间超过 24 小时的订单商品，并分批请求 Ozon。不得因为进入订单页而重复读取所有已有图片。

### 类目与属性

类目树缓存 24 小时。商品上架页面先读取本地类目；缓存过期才后台刷新。属性按 `category_id + type_id` 缓存，属性字典值使用相同键加 `attribute_id` 缓存；在有效期内不重复调用 Ozon。

## 后端接口

新增统一接口：

`POST /api/v1/shops/{shop_id}/auto-sync`

请求体包含 `view`，只能使用后端定义的页面枚举。返回每个资源的决定：`fresh`、`started`、`already_running` 或 `failed_to_start`，不得等待长同步完成。前端随后仍从本地读取业务数据，并可在状态提示中显示“本地数据时间”和“后台校正中”。

保留人工同步入口，但改名为“强制校正”。它必须显式选择资源；完整商品校正属于人工动作，不由普通页面进入触发。

## 并发、失败与恢复

- 同店铺同资源同一时刻只能有一个有效租约；获取租约必须在数据库事务中完成。
- 任务异常或进程退出后，租约到期可被下一次触发接管。
- 只有完整成功处理本轮范围后才更新 `last_success_at`；失败保留旧成功时间和游标，并在 `sync_runs`、`sync_states.last_error` 记录脱敏错误。
- Ozon 认证错误不密集重试；限流和服务错误使用带抖动的指数退避。
- 页面始终保留并展示已有本地数据，后台校正失败只显示非阻塞告警，不清空列表。

## 安全与写回边界

本设计只覆盖 Ozon → ERP 的只读校正。自动触发不得调用库存、价格、营销、发货或商品发布写接口。未来写回仍必须经过预检、审批、审计和灰度控制，不能复用本自动只读入口绕过审批。

## 验收标准

1. 选择店铺后页面先显示本地数据；超过 5 分钟时后台触发对应资源校正。
2. 5 分钟内重复进入同一页面不会产生新的 Ozon 请求。
3. 两个标签页同时触发时，同店铺同资源只创建一个有效同步任务。
4. FBS 订单使用 10 分钟重叠窗口并幂等更新状态，成功后推进窗口。
5. 商品从持久化分页游标继续，普通自动校正不会每次重扫全部商品。
6. 已有订单图片在 24 小时内不重复请求；类目树在 24 小时内不重复刷新。
7. 后台失败不会清空本地列表，错误可在同步中心查看且不包含凭据。
8. PostgreSQL 完成迁移后可启动 API；SQLite 测试套件继续通过。
9. 前端选择店铺和切换左侧页面都能触发正确的资源映射，并显示本地数据时间/校正状态。

## 非目标

- 本阶段不实现 Ozon 写回。
- 本阶段不实现复杂分布式调度平台；采用数据库租约和应用内后台任务，后续负载增长时再迁移到独立 worker/队列。
- 不承诺商品 API 提供不存在的更新时间增量能力；商品使用可恢复的滚动分页校正。
